What 1.7.0 contains (from [the release notes](../RELEASE_NOTES.md#170)):

- **R110, raised limits.** Unique vertices, faces and wires per document go from 100,000 to 300,000, and unique edges
  from 300,000 to 900,000. A component definition is limited to 200,000 vertices, faces and wires and 600,000 edges.
  The document chunk goes from 32 MiB to 96 MiB, the file from 128 MiB to 256 MiB, and the undo history from 64 MiB to
  192 MiB. The durable outcome budget goes from 268,812,472 to 403,030,200 bytes. The materialized limits, the placement
  limit and the per-body kernel limits do not change. A raw JSON file keeps its 128 MiB limit.
- **R111, unused definitions.** `component.delete_definition` removes one unused definition, and `document.purge_unused`
  removes, in one edit, the unused definitions, materials and assets. Both are scripting commands. The desktop interface
  and the desktop assistant do not change.

The downgrade check uses the published 1.6.1-1 CLI, unpacked privately, which reads `readDocumentVersions` 1 to 35 and has
`documentVersion` 35. On each of the three official machines it opened 17 files unchanged, with no refusal, and it
accepted the sheet-free save. The files were the six committed fixtures (`presentation-v30`, `edge-styles-v31`,
`geographic-site-v32`, `material-texture-size-v33`, `terrain-dem-v34` and `reference-geo-v35`), each saved again by 1.7.0

schema-28 component parameters; and the schema-27 drawing sheets. The 1.6.1 record also had 17 opens. Each open is
recorded only after the validation, the open and a byte comparison succeed.

The R111 purged file (a 1.7.0 save within the 1.6.1 limits, from the rollback lifecycle) also opened unchanged in the
1.6.1 CLI: `valid` true, `documentVersion` 26, exit 0.

**Refusal of the 153,000-vertex model.** The 1.7.0 CLI writes a model of 153,000 unique vertices (one 9,000-point face,
then a linear `geometry.array_selection` with count 16, 17 bodies), and the 1.6.1 CLI refuses it with exit status 1, the
file unchanged (`cmp`), and this text, the same on each machine:


## Memory evidence

[R082w v3](R082w-memory-budget-v3.md) is the memory record for the raised limits. It is **software-only**. It was measured
in a Release build, on one CPU with 4 GiB, under llvmpipe (no GPU), and the viewport figures are software frame times.

Measured (process peak RSS, wall-clock times):

- the loose unique family at 300,000 unique vertices (5,769 prisms, 299,988 unique vertices, no placements): peak 1,826 MiB
  (1.92 GB), load 1.24 s, save 1.44 s, frame p95 493 ms (software);
- the densest shape, three closed 100,000-face spheres in one component (150,006 vertices, 300,000 faces, 450,000 edges):
  peak 974 MiB, load 2.52 s, save 1.23 s (core only, no viewport);
- an 89 MiB file (document chunk 89.1 MiB, bound 96 MiB): read and load 1.51 s in a fresh process, save 1.53 s, peak
  1,391 MiB at the end (905 MiB after load);
- a whole-document edit of 5,700 of 5,769 bodies in one edit, charged 191.0 MiB of history, kept in history at 297 MiB
  resident (undo 0.01 s, redo 0.01 s). Moving all 5,769 bodies in one edit is refused by the 192 MiB budget.

Modeled worst case: 3.03 GiB with the 192 MiB undo row. With the measured excess for the unique shape, 3,839,057,776 bytes,
or **3.58 GiB**, which is 178.8 MiB under the 3.75 GiB ceiling. With the 150 MB hardware delta that v1 measured, about
**3.72 GiB**, which is 35.7 MiB under the ceiling and under the 4 GiB operational job cap. The release notes round the
margins to 179 MiB and 36 MiB.

**Not measured:** the frame time of the file-loaded document and of the whole-document edit (c and d); a viewport frame
time for the densest shape (b2); any hardware frame time, history or file timing at the raised limits (D-091); and the
history charge of a 300,000-face component edit, which the component definition limit now makes unreachable. The
hardware evidence waiver of [ADR 0161](../decisions/0161-m9-hardware-evidence-waiver.md) still applies to the raised
limits. The owner raised the modeled ceiling from 3 GiB to 3.75 GiB on 2026-11-01, and the 4 GiB operational job cap did not
change.
